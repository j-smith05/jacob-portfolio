The Problem

Any server with SSH open to the internet gets hammered by automated login attempts. The evidence sits in the sshd log, but at hundreds of thousands of lines it’s too much to read. The goal was to build a tool that could answer questions like which IPs are attacking hardest?, which accounts are they guessing?, and when do attacks peak?, without loading the whole log into memory.

How It Works

  1. 1. Clean the raw log

    Raw sshd lines were trimmed down to the fields that matter: date, time, event type, user, and IP.

    # raw
Dec 12 18:58:26 LabSZ sshd[31243]: Failed password for invalid user zouzhi from 115.71.16.143 port 38790 ssh2
# cleaned
12/12 18:58:26 Failed zouzhi 115.71.16.143

  2. 2. Build disk-based B-Trees

    Each line became a key such as Failed-115.71.16.143 or Invalid-04:05. Keys went into a B-Tree stored on disk, one node per block, so the tree can grow far beyond available memory. Inserting a key that already exists bumps its count instead of adding a duplicate, so the tree ends up holding a frequency table. We built nine trees, one for each question: failed, accepted, and invalid-user attempts by IP and by time, reverse-DNS warnings, and user/IP pairs.

  3. 3. Cache hot nodes

    Disk reads are the bottleneck, so an LRU cache keeps recently used nodes in memory. Attack traffic repeats the same few IPs over and over, which is exactly the access pattern a cache handles well.

  4. 4. Query and rank

    An in-order walk of each tree writes its keys out in sorted order, and the results load into SQLite so “top 25 attacking IPs” is a single query. Every dump and search result was checked against the reference output, and the full test suite passed on an AWS EC2 instance.

What the Data Showed

A handful of IPs did most of the work

1,007 different IPs failed a login, but the top 10 alone sent 104,532 attempts, nearly two thirds of the total. The busiest single address tried 17,340 times. That pattern points to a few automated brute-force bots, not a broad crowd of attackers.

Failed login attempts per IP. Seven of the top ten share the 183.x prefix.

Root was the main target

87% of failed attempts (139,818) went after the root account. When bots guessed names that don’t exist on the server, they reached for default and service accounts:

  • admin · 3,042
  • test · 543
  • oracle · 489
  • support · 451
  • pi · 322
  • nagios · 296
  • guest · 259
  • postgres · 216

That list reads like a checklist of software installed with default credentials: Raspberry Pi, Oracle, Nagios, PostgreSQL.

Attacks peaked in the early morning

Failed attempts climbed through the night and peaked at 4 AM server time with 13,143 attempts, more than four times the quietest hour (10 PM, 3,019). The busiest single day, Jan. 3, logged 27,154 failures.

None of the brute force got in

Only 181 logins succeeded (0.09% of events), all to nine named user accounts and never to root. Eight IPs show up in both the failed and accepted lists, but each had at most seven failures, almost all on the same account it later logged into. That looks like legitimate users mistyping a password. None of the high-volume attacking IPs ever logged in.

What I’d Recommend for This Server

The data points to a few cheap defenses that would have stopped nearly all of this traffic:

  • Disable root login over SSH (PermitRootLogin no), which removes the target of 87% of attempts
  • Use key-based authentication only, so password guessing can’t succeed at all
  • Rate-limit or ban repeat offenders with a tool like fail2ban; ten IPs sent two thirds of the traffic
  • Remove or lock default accounts such as admin, test, and pi
